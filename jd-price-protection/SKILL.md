# 京东价格保护

为用户真实既有消费订单申请符合当前规则的价格保护，并如实报告退款进度。网站决定资格和赔付金额；有按钮不等于可申请或一定获赔。

## 工具与授权

- 使用宿主 Agent 已有的浏览器导航、页面读取、点击工具，DOM、快照或截图均可。不依赖特定插件、操作系统、私有 API、Cookie 导出或固定账户。
- 遵循宿主浏览器的后台操作、页面所有权和用户接管规则，优先复用本任务页面。需要登录/验证时交接现有页面，用户明确完成后恢复。
- “检查/研究价保”只读；用户要求“申请价保/帮我保价”时可在指定订单范围内直接申请，不重复询问已给出的授权。未指定范围则检查当前账户已有订单；账户或订单范围有歧义时先澄清。
- 不新建订单、不为价保购买商品、不取消订单或退货，不提现、转账、开通金融产品或编造降价证据。
- 申请记录行内的「删除」属于平台记录管理，不属于价保流程，不要触碰。

## 入口与识别

申请页：<https://pcsitepp-fm.jd.com/>；导航路径：我的京东 → 客户服务 → 价格保护。

官方规则：<https://help.jd.com/user/issue/291-4537.html>。资格和有效期以该订单及当前规则为准，不硬编码“所有订单30天”。

1. 打开页面，确认登录账户和订单列表加载完成。列表固定为“最近三个月订单”，没有分页；更早的订单只能用搜索框（`input[name="keyWords"]`，提示语为订单号）定位。报告时说明实际覆盖范围。
2. 等判定稳定再读。页面先渲染商品行，再异步补上限制说明和按钮状态——实测约 300ms 时行内既没有过期说明、也没有按钮灰化样式，约 600ms 后两者一起到位。稳定前读到的价格和状态都不可信：同一行曾在渲染中途读出另一个价格。
3. 逐行读取商品、订单尾号、有效期、限制说明和申请入口。页面出现的状态文字有 `该商品已超过价保周期，有效期至…`、`商品为赠品，不支持价保！`、`该订单不支持价保服务，请您谅解。`。赠品和不支持价保的商品根本没有按钮。
4. 每个可申请项对应唯一按钮 id：`#applyBT_{订单号}_{skuId}_1`（如 `#applyBT_3650246019924350_100259193050_1`）。用它精确定位到具体商品行，不要按“申请价保”文字批量匹配。
5. 能否点击的机器判据：可申请项的内联 `style` 为空；不可点击项（过期、已失效）带灰化内联样式 `border: 1px solid rgb(200, 200, 201); color: rgb(200, 200, 201); cursor: default;`，按钮文字仍在，但点击无效。读按钮的 `style` 属性比解析中文说明文本更可靠。
6. 当前商品价格低于购买价格不保证可赔，支付券/特殊活动等可能不计入价保。不要自行把两个展示价格相减当作已退款额。

## 提交与核对

1. 先记录符合条件的候选和已有申请状态。准备提交时，写入一次本地尝试标记（若宿主支持文件），含时间、动作、任务页面标识及本地订单/商品标识；完整标识只留用户私有存储，报告使用脱敏值。不要写进技能安装目录或公开仓库。
2. 点击前重新确认该按钮当前没有灰化（内联 `style` 为空），再点击一次。不得批量点击页面所有同名按钮。
3. 成功后弹出全屏遮罩 `.m-success-dialog-wrap`，文字形如“恭喜您价保成功! 为您节省N元”。它靠 `closeSuccessTip(遮罩id)` 关闭（绑在遮罩内的图片元素上），不关闭会持续拦截后续点击，表现为 `intercepts pointer events`。
4. 进入“价保申请记录”，按订单号与申请时间把结果匹配回本次商品。记录页字段为：商品 / 订单编号 / 申请时间 / 下单时价格 / 数量 / 价保时价格 / 价保数量 / 价保金额 / 申请状态，另有时间筛选（近三个月 / 今年 / 2025年 / 2024年）和状态筛选（全部状态 / 申请成功 / 申请失败 / 处理中）。
5. 记录行的“查看详情”调用 `queryRefundDetail(订单号, skuId, 1, 金额, 1, 时间戳)`，在页内展开“价保退款详情”，字段为：申请时间 / 退款金额 / 到账周期 / 返还方式 / 退款状态。同行的“删除”调用 `deletePropRecord(记录id)`，不要点。
6. 申请入口页和记录页是两个页面：记录页是整页跳转到 `api.m.jd.com/api?...functionId=siteppPC_pricerecord`（带一次性 token），不是同页切换。看完记录要回申请页，重新导航到 <https://pcsitepp-fm.jd.com/>。
7. 如存在正常可访问的个人钱包/原支付账户流水入口，做只读核验。找不到时停留于平台退款状态，不为核验去开通产品。已观察到官网页脚“京东钱包”会打开商户支付平台，不能将其当成个人钱包余额。
8. 退款可能分次或合并返还。核对到账时使用退款关联信息与流水，不要求一条流水恰好等于总金额；没有关联证据的余额变化不能单独证明到账。

## 两处展示口径差异

- **价格**：申请页显示商品标价，记录页显示“下单时价格 / 价保时价格”，两者不同源。实测同一商品分别显示 ￥1,005.00 与 ￥977.00 / ￥974.00，不要手工相减。
- **到账周期**：提交后的行内提示为“1~7个工作日”，退款详情为“1个工作日到账”。两处都保留来源，优先报告退款详情的值。

## 结果口径

| 状态 | 可以报告 | 不能推断 |
| --- | --- | --- |
| 已提交/审核中 | 已申请，等待审核 | 已获赔、已到账 |
| 价保成功 | 平台批准的差价金额 | 钱已进入钱包或银行卡 |
| 退款详情显示已退款成功 | 平台显示退款成功，附返还方式 | 已独立核对个人资金流水 |
| 匹配到实际入账流水 | 已到账，注明渠道和核验依据 | 所有退款都返至银行卡 |
| 用户明确确认到账 | 用户确认到账 | Agent 独立核验到账 |

报告金额使用网站核定值，返还形式可能为钱包余额、其他支付渠道或京豆，不能全部记为现金。没有获赔属于正常结果。

## 中断与重复申请

- 超时、断连或不明结果先查申请记录，不立即重试。若仍不能确定是否已提交，保存“结果待核实”，停止该商品的提交。
- **按钮状态不能当防重依据**。申请成功后行内会短暂显示“已申请”，但重新加载页面后按钮恢复为正常的可点击“申请价保”，判定条件与未申请时完全一样。此时页面留下的唯一痕迹是追加的说明文字：
  - `该商品已成功申请价保1次，金额：N。`
  - `该商品于{时间}申请价保成功，金额：N元。`
  每次判定候选前都要同时读这些说明，否则同一商品会被重复提交。
- 恢复时先读取本次记录与网站现状，再决定下一步。已经成功的这一笔不要重复提交；未来再次降价属于新检查，只有确认新的可申请条件、遵守平台次数限制并在用户授权范围内才可发起。
- 优先保存：阶段、订单/商品本地标识、尝试时间、申请状态、金额、退款方式、退款详情状态、独立到账核验与证据位置、下一步。不要把用户数据写进 Skill 安装目录或公共仓库。
- 最终列出检查范围、成功/待审核/跳过项、平台退款金额、实际核验程度。按宿主规则结束浏览器任务；需用户验证时保留页面与断点。不要自行安排每日定时任务。
